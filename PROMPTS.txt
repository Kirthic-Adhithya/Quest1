================================================================================
LLM PROMPTS USED
================================================================================

The problem statement requires documenting any prompts used while building this
solution. Listed below are the prompts that materially shaped the design or the
code -- scoping decisions, bug reports that led to real fixes, and requests that
changed the architecture. Purely operational exchanges (running a command,
checking a status, asking where a file is) are omitted; they didn't shape the
project and would only add noise here. Wording has been lightly cleaned up for
clarity where the original had typos or was written in a hurry; the intent and
substance are unchanged.


--------------------------------------------------------------------------------
1. SCOPING THE PROBLEM AND PROPOSING AN INITIAL APPROACH
--------------------------------------------------------------------------------

    I have a project folder where I'm building the solution described in the
    attached problem statement. There's an ambiguity I want to resolve first:
    does "find the frame where the dialogue is spoken" mean the first dialogue
    that appears on screen (someone visibly speaking, in frame), or does it
    mean locating the specific input dialogue string regardless of whether the
    speaker is visible?

    My proposed approach: transcribe the audio to text with timestamps, filter
    to frames where dialogue is being spoken, then further filter to frames
    where a human is visibly present. A related ambiguity: should a masked or
    turned-away person still count as "on screen"? From the remaining
    candidates, find the closest text match to the target dialogue and return
    it -- or return the first result if the task is asking for the first
    dialogue overall.

    Before writing any code: is this approach sound? And can you set up the
    project's folder structure, plus a minimal script in the right place that
    takes a URL as input and confirms it's received correctly?

Used for: resolving the "first on-screen dialogue vs. given input dialogue"
ambiguity, critiquing the person-detection step in the proposed pipeline, and
generating the initial repository scaffolding.


--------------------------------------------------------------------------------
2. CORRECTING THE INTERPRETATION AFTER WATCHING THE VIDEO
--------------------------------------------------------------------------------

    I watched the reference video. The line is spoken at exactly 5:26, and
    there's no on-screen text at that point. Before that, there's title and
    cast-name text on screen that isn't the answer, and several moments where
    a person is facing the camera and speaking but isn't saying the target
    line either.

Used for: overturning an initial OCR-first hypothesis in favour of audio as the
primary signal, and deriving the detector-vs-discriminator principle (match
against the specific target text, rather than detect generic "dialogue is
present") that removed the person-detection and speech-presence filters from
the design.


--------------------------------------------------------------------------------
3. VALIDATING THE REVISED APPROACH AND RESOLVING A SECOND AMBIGUITY
--------------------------------------------------------------------------------

    Does the revised approach work end to end? If not, walk through what
    would.

    There's still an ambiguity in "on-screen dialogue": does it require the
    speaker to be visibly facing the camera, or just that the line is spoken
    at that point in the video? I think it should be the latter -- that's the
    interpretation with genuine real-world application (subtitle alignment,
    clip search, dubbing), since none of those care whether a face happens to
    be in frame.

Used for: a stage-by-stage review of the pipeline (kept ASR + fuzzy matching,
dropped person/speech-presence filters, added forced alignment as a precision
stage), and confirming the "on-screen dialogue" reading that DESIGN.md documents.


--------------------------------------------------------------------------------
4. LANGUAGE GENERALITY AND REPOSITORY HYGIENE
--------------------------------------------------------------------------------

    Does this also work for languages other than English, or just the
    reference video's? And separately -- the folder structure has grown a
    lot; are all of these files actually necessary? Remove anything that
    isn't.

Used for: testing whether stage 3 (language-agnostic) and stage 4 (forced
alignment) actually held up across scripts -- found and fixed a real crash on
non-Latin text via romanisation -- and for a repository audit that removed two
dead stub files and confirmed the rest were genuinely in use.


--------------------------------------------------------------------------------
5. A REAL DOWNLOAD FAILURE, REPORTED AS A BUG
--------------------------------------------------------------------------------

    Running the CLI against the reference video produced repeated connection-
    reset and "unable to rename file" errors partway through the download,
    ending in a crash rather than a clean result. Investigate and fix it.

Used for: root-causing two separate, real bugs in the download path -- a
Windows file-lock race between antivirus scanning and yt-dlp's fragment
renaming, and yt-dlp's default of silently discarding a permanently-failed
fragment while still reporting success, which had produced a video several
minutes shorter than every previously verified download with no error at all.


--------------------------------------------------------------------------------
6. UNEXPLAINED "NO OUTPUT" WHILE RUNNING INDEPENDENT TESTS
--------------------------------------------------------------------------------

    I'm running some test cases of my own alongside this session, but I'm not
    getting any output -- can you look into what's happening? [After the
    cause was found:] Stop all of the running processes.

Used for: discovering that multiple pipeline instances were running
concurrently and exhausting the GPU's memory, which produced severe stalling
rather than any error message. This directly motivated the web app's later
single-worker job queue, which processes one video at a time by design rather
than one thread per request.

7. REQUESTING A SIMPLIFICATION PASS AND A FULL REPOSITORY WALKTHROUGH
--------------------------------------------------------------------------------

    Is the code fully simplified at this point, or is there more to clean up?
    If there's anything left to simplify, do it. Once that's done, walk me
    through the entire repository -- what every file, function, and import
    does.

Used for: a real dead-code audit that removed an unused convenience function,
an unused method whose logic had been superseded, and duplicated logic across
two call sites; followed by a complete, file-by-file explanation of the codebase.


--------------------------------------------------------------------------------
8. SINGLE-VIDEO CACHING FOR DEPLOYMENT
--------------------------------------------------------------------------------

    When I download a different test video, the previous one isn't removed --
    its files and cache entry are both still sitting there. For deployment I
    want this to use as little disk space as possible, so please make sure
    switching to a new video actually cleans up the old one.

Used for: changing the media cache from "keep every video ever fetched" to a
single-video-at-a-time policy, evicting the previous video's download, audio,
and transcript whenever a new URL is requested.


--------------------------------------------------------------------------------
9. REDUCING OVERALL DISK FOOTPRINT
--------------------------------------------------------------------------------

    What's actually taking up so much disk space in this project, and is it
    possible to reduce it?

Used for: a full breakdown of disk usage across the virtual environment, model
cache, and media cache, which surfaced a real ~2GB duplication -- two separate
copies of the same CUDA libraries installed for two different reasons -- and
fixing it by pointing both consumers at the same copy.

10. QUESTIONING WHETHER THE ALIGNMENT STAGE IS NECESSARY
--------------------------------------------------------------------------------

    Is the forced-alignment model actually required, or could the pipeline
    work without it? What does it concretely add? Is there a risk it makes
    the result less accurate than it should be? And separately -- instead of
    caching the Whisper model locally, could it be called over the internet

Used for: a quantified justification of the alignment stage (measured
precision gap against relying on ASR timestamps alone) and an honest
comparison of local inference against a hosted transcription API, covering
disk, latency, cost, privacy, and offline capability trade-offs.

11. REQUESTING A WEB FRONTEND AND BACKEND
--------------------------------------------------------------------------------

    I want a backend and frontend for this so I can run it from a browser on

12. AN EXPERIMENTAL METHOD FOR TUNING THE MATCH THRESHOLD
--------------------------------------------------------------------------------

    I raised the match-score threshold from 80 to 90 because a test case
    returned the wrong dialogue. Here's an idea to find the right value
    properly: check whether there's a score band (say, above 95, then 90-95,
    then 85-90) above which every match is genuinely correct, since I suspect
    the same correct sentence can score both above and below 90 depending on
    the run. Run some real test cases and find where that boundary actually
    is, rather than guessing.

Used for: an empirical investigation that confirmed the hypothesis -- a
documented, previously-verified genuine match had scored 89.3 in one run, so
raising the threshold to 90 would have rejected a correct answer -- and led to
settling on a value informed by real test data instead of intuition.


--------------------------------------------------------------------------------
13. CATCHING A BOUNDARY BUG IN THE THRESHOLD FIX
--------------------------------------------------------------------------------

    What if the threshold were 81 instead?

Used for: catching a real off-by-one in the matching logic -- the survivor
check accepts a score equal to the threshold, so a threshold of exactly 80 did
not actually reject a false positive that had scored exactly 80.0. This one
value change was the fix; the reasoning is recorded in DESIGN.md.

16. RECONSIDERING SCOPE: BUILDING, THEN REMOVING, AN OCR SEARCH PATH
--------------------------------------------------------------------------------

    An on-screen-text search path (OCR, as a second way to locate the
    dialogue alongside ASR) was built and debugged in this session. On
    review: is running both an OCR and an ASR search overkill here, or
    could this be exactly what evaluators are checking for -- doing what
    the client-side requirements actually call for, without over-engineering?

Used for: reverting the OCR path entirely -- the extraction module, the
on-screen-text matching functions, the CLI/web source selector, and the
now-unused dependencies. The problem statement gives the dialogue as spoken
text to search for; a second full search modality wasn't something it asked
for, and the project's own stated design principle (match the specific
target, don't build detectors you don't need) argued against keeping it.
Quality selection, requested in the same original prompt, was kept -- it's a
small, genuinely useful option, not a second search modality.
