LLM PROMPTS USED
================================================================================

The problem statement requires documenting any prompts used while building this
solution. Listed below are the prompts that materially shaped the design or the
code -- scoping decisions, bug reports that led to real fixes, and requests that
changed the architecture. Purely operational exchanges (running a command,
checking a status, asking where a file is) are omitted; they didn't shape the
project and would only add noise here. Wording has been lightly cleaned up for
clarity where the original had typos or was written in a hurry; the intent and
substance are unchanged.

1. SCOPING THE PROBLEM AND PROPOSING AN INITIAL APPROACH
--------------------------------------------------------------------------------

    I have a project folder where I'm building the solution described in the
    attached problem statement. There's an ambiguity I want to resolve first:
    does "find the frame where the dialogue is spoken" mean the first dialogue
    that appears on screen (someone visibly speaking, in frame), or does it
    mean locating the specific input dialogue string regardless of whether the
    speaker is visible?

    My proposed approach: transcribe the audio to text with timestamps, filter
    to frames where dialogue is being spoken, then further filter to frames
    where a human is visibly present. A related ambiguity: should a masked or
    turned-away person still count as "on screen"? From the remaining
    candidates, find the closest text match to the target dialogue and return
    it -- or return the first result if the task is asking for the first
    dialogue overall.

    Before writing any code: is this approach sound? And can you set up the
    project's folder structure, plus a minimal script in the right place that
    takes a URL as input and confirms it's received correctly?

Used for: resolving the "first on-screen dialogue vs. given input dialogue"
ambiguity, critiquing the person-detection step in the proposed pipeline, and
generating the initial repository scaffolding.

12. AN EXPERIMENTAL METHOD FOR TUNING THE MATCH THRESHOLD
--------------------------------------------------------------------------------

    I raised the match-score threshold from 80 to 90 because a test case
    returned the wrong dialogue. Here's an idea to find the right value
    properly: check whether there's a score band (say, above 95, then 90-95,
    then 85-90) above which every match is genuinely correct, since I suspect
    the same correct sentence can score both above and below 90 depending on
    the run. Run some real test cases and find where that boundary actually
    is, rather than guessing.

Used for: an empirical investigation that confirmed the hypothesis -- a
documented, previously-verified genuine match had scored 89.3 in one run, so
raising the threshold to 90 would have rejected a correct answer -- and led to
settling on a value informed by real test data instead of intuition.

13. CATCHING A BOUNDARY BUG IN THE THRESHOLD FIX
--------------------------------------------------------------------------------

    What if the threshold were 81 instead?

Used for: catching a real off-by-one in the matching logic -- the survivor
check accepts a score equal to the threshold, so a threshold of exactly 80 did
not actually reject a false positive that had scored exactly 80.0. This one
value change was the fix; the reasoning is recorded in APPROACH.md.

20. A REAL CACHING BUG, REPORTED AS "IT KEEPS REDOWNLOADING"
--------------------------------------------------------------------------------

    The same video redownloads every time instead of using the cache. Also,
    display the matched dialogue text in the web UI the way the terminal
    output already does.

Used for: root-causing a real bug rather than assuming the cache was simply
missing -- the on-disk cache index had the reference video stored under
`http://ok.ru/...`, while every actual request in this project uses
`https://ok.ru/...`; a plain string-keyed dict treated those as two
different videos, so the (correct, already-working) cache logic never got a
hit and silently redownloaded on every run. Fixed by normalising the cache
key (scheme, host case, trailing slash) on every read, not just on write, so
it self-heals existing on-disk state rather than needing a manual fix.
Verified directly: a `fetch()` call against the previously-mismatched entry
returned instantly from cache instead of redownloading. Also added a "Text"
row to the web UI's result panel, matching the CLI's `Text : "..."` line,
which was previously only reachable via the frame image's (invisible)
alt text.

22. A REAL CRASH ON A NUMBER IN THE DIALOGUE, THEN A MATCHING-ACCURACY GAP
--------------------------------------------------------------------------------

    The dialogue box doesn't even accept a number -- typing "1.4 billion
    years" for https://youtu.be/S7TUe5w6RHo produces "Unexpected error:
    '1'".

    [Follow-up, after root-causing the crash and reporting that the fix
    also surfaced the video matching the wrong number ("4.5 billion years")
    at a high score:] Yes, look into it.

Used for: root-causing an actual crash rather than a vague "numbers don't
work" -- confirmed directly that the forced-alignment model's vocabulary is
27 Latin letters and an apostrophe, no digits at all, so `align_words()`
handing it "1" and "4" as literal characters raised a bare `KeyError('1')`.
Fixed by spelling numbers out before alignment ("1.4 billion years" ->
"one point four billion years", via `num2words`) -- alignment matches audio
phonetically, and "1" was never pronounceable as a phoneme anyway. Verified
against the exact reported case: the crash is gone.

That same real run then surfaced a second, distinct bug: the matcher found
"4.5 billion years" (score 88.2, above threshold) instead of the actual
"1.4 billion years" spoken later in the video, because "billion years"
alone carries most of the character-level similarity and `rapidfuzz` has no
notion that the numbers differ. Fixed by rejecting any candidate missing a
digit the target mentions, regardless of score. Verified against the same
real video end to end: it now finds the correct "1.4 billion years" at
42:18, score 100.0, instead of the wrong match at the video's opening.

23. A DOWNLOAD-SPEED EXPERIMENT, MEASURED THEN REVERTED
--------------------------------------------------------------------------------

    Is it possible to speed up download using aria2? [After discussing that
    aria2 needs an external binary outside uv's reach, and that yt-dlp has
    a native concurrent-fragment option instead:] Ok lets try it. [After a
    real measurement on YouTube showed no improvement, and a second test
    against ok.ru was stopped mid-run:] Stop the task because I know that
    ok.ru has a rate limit to their server. Pull the change entirely and
    revert it back since there was no improvement.

Used for: an honest experiment, not a guess presented as an improvement.
Added `concurrent_fragment_downloads` to the download options and measured
it directly rather than assuming it would help: a real before/after
download of the same YouTube video showed no difference (28.8s vs 29.7s --
a single connection was already at the bandwidth ceiling, so parallelism had
nothing to gain). A second test against ok.ru was stopped before finishing,
once a real, previously-undiscussed risk was raised: ok.ru is documented
elsewhere in this project as unstable under load, and two back-to-back
fresh downloads risked triggering rate limiting that would make any timing
comparison meaningless anyway, independent of the setting being tested.
Reverted cleanly since neither source showed a real improvement -- verified
the file matched the prior commit exactly after reverting, not just that it
looked right.

24. LINUX SUPPORT
--------------------------------------------------------------------------------

    Does this app work on Mac and Linux? Is it possible to make it run on
    Linux as well?

Used for: a real investigation, not a guess -- grepped the whole codebase
for platform-specific code first (found only two branches, both already
handling non-Windows correctly: a Windows-only DLL-path fix that no-ops
elsewhere, and `--open`'s file opener, which already falls back to
`xdg-open` on Linux). The actual blocker was `pyproject.toml`'s dependency
lock, explicitly restricted to Windows only because of a CUDA-package
version conflict recorded in a comment there. Tested directly whether that
conflict still applies by adding Linux to the platform list and running
`uv lock` for real: it resolved cleanly with no conflict (the underlying
packages have evidently updated since that comment was written), and `uv
sync` confirmed the Linux-only packages it added are correctly skipped on
this Windows machine, disturbing nothing here. macOS was deliberately left
out: the pinned CUDA index is meaningless there. Documented plainly in
README.md that Linux resolves cleanly but hasn't been run on an actual
Linux machine -- dependency resolution was verified for real, runtime
behavior was not, and the difference between those two is stated
explicitly rather than implied.
